# P1-C 저장 실패 기준선 및 완료 계약
2026-11-23 · feature/core-modular-architecture · 기준 b545155.
사용자 지시로 검증된 b545155까지 origin/feature/core-modular-architecture에 푸시했다. PR/기본 브랜치 병합 없음. 이번 후속 작업은 실패 주입 검사와 계약 설계이며 런타임 변경이 아니다.

## 실제 저장 흐름
main 조사 실행 → 메모리 증거 변경 → 기존 World.save_world → checkpoint → Store.replace.
checkpoint는 여러 prepare를 호출하고 snapshot.saved만 갱신한 후 파일 교체 성공 시 w.saved를 갱신한다. prepare가 일부 상태를 정규화할 수 있으므로 실패 시 전체 메모리 무변이를 보장하지 않는다.
replace는 스키마/미래 버전 검사 → .tmp 쓰기/검증 → .bak.tmp 복사 → .bak 교체 → primary 교체 순서다. 마지막 primary 교체 이전에 backup이 갱신될 수 있으므로 모든 실패 단계에서 primary와 backup이 모두 동일하다고 일반화하면 안 된다. 현재 형식에는 fsync 기반 전원 손실 내구성 보장이 없다.
기존 main은 조사 메시지를 저장 결과와 별개로 표시한다. 저장 실패가 조사 실패로 자동 롤백되거나 재시도되는 것은 아니다.

## 신규 실패 주입 검사 — 검증 완료
합성 테스트 디렉터리만 사용했다. .tmp와 .bak.tmp 위치에 디렉터리를 만들어 실제 파일 생성/복사를 실패시킨다. production 코드에 테스트용 장애 분기를 넣지 않는다.
각 단계에서 저장 반환 false, w.saved 유지, 메모리의 새 증거 유지, 기존 primary/backup bytes 보존, 디스크에 미저장 증거가 없음을 검사한다. 장애를 제거한 뒤 도메인 행동을 다시 실행하지 않고 checkpoint만 재시도하여 동일한 증거와 이벤트가 한 번만 저장되는지 검사한다. 같은 checkpoint의 반복 저장도 검사한다.
추가로 v24 합성 원본을 놓고 v23 저장기가 timestamp/원본 bytes를 유지하며 거부하는지 검사한다.
신규27개 + 기존1031개 = 전체1058 PASS, 실패0. 로그의 저장 실패/copy 오류는 의도적으로 주입한 경로에서 예상되는 진단이며 check 실패와 구분한다. 최초 테스트의 메모리 int vs JSON float 비교 문제는 기대 레코드도 JSON 왕복 정규화해 해결했으며 모든 필드 비교를 유지했다.
신규 코드: desktop/tests/test_chapter1_save_failure.gd. 기존 Runtime/main/world/store/RPC 변경 없음. ENet·GUI·서버 재시작 검사는 이번에 재실행하지 않았다.

## 후속 구현 계약 — 명세 확정, 미구현
채택 방향은 기존 동작과 호환되는 **메모리 상태 유지 + 명시적 미저장 표시 + checkpoint 재시도**다. 공유 월드 전체를 이전 snapshot으로 롤백하면 다른 인물의 이후 변경을 지울 위험이 있어 범용 롤백을 도입하지 않는다.

| 구분 | 의미 | 후속 처리 |
|---|---|---|
| domain_recorded | 이번 요청으로 메모리에 새 증거가 생김 | 저장 성공과 별개, 도메인 재실행 금지 |
| checkpoint_ok | 해당 시도에서 검증된 snapshot의 파일 교체가 성공 | saved 시각 갱신; 전원 손실 내구성까지 의미하지 않음 |
| pending_save | 메모리 변경을 디스크에 반영하지 못함 | 사용자에게 미저장 상태 표시, 수동/제한된 재시도 제공 |
| blocked_save | 미래 버전/유효성/경로 문제 등 해결 필요 | 원본 보존, 무한 재시도 및 초기 파일 덮어쓰기 금지 |

후속 저장 서비스는 저장소별 pending 상태를 소유하고 연결 peer별로 분리하지 않는다. single/server는 동일 checkpoint 규칙을 호출하고 client는 저장 권한을 갖지 않는다. pending/최근 오류는 실행 상태로 시작하며 현재 v23 데이터에 새 필드를 추가하지 않는다.
현재 save_world의 bool만으로 원인을 정확히 분류할 수 없다. 첫 구현에서는 실패를 일반 저장 실패로 표시하고 임의로 '디스크 용량 부족' 등 추정하지 않는다. 구체적 오류 분류는 Store 반환 계약 영향 조사 후 별도 추가한다.
도메인 이벤트를 재실행해 저장을 재시도하지 않는다. 재시도는 현재 권한 월드의 checkpoint만 수행한다. 종료 전 실패 시에도 저장되었다고 표시하지 않는다. 서버 전체 pending 표시의 클라이언트 전달은 기존 snapshot 공개 필드/프로토콜 영향 분석 이후 진행한다.

## Core 이벤트·추가 한계
현재 recorded 플래그를 영구 완료 이벤트로 전환하지 않는다. 프로세스 재시작까지 exactly-once가 필요하면 영구 outbox/처리 영수증과 실패 원자성 설계가 먼저 필요하며 단순 Signal만으로 보장할 수 없다. 이번 계약은 해당 기능을 구현한 것이 아니다.
검사한 실패는 staging open/copy와 미래 버전 거부다. 실제 디스크 가득 참, flush 실패, 마지막 rename 실패, 전원 손실, 동시 writer의 원자성은 미검증이다. Store는 동시 다중 writer 안전을 보장하지 않으므로 월드 저장 writer를 하나로 유지해야 한다.
